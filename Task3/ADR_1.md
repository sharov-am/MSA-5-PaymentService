# Шаблон ADR 
## Общая информация 

1. Родительский артефакт - нет
2. Статус - В проработке

## Контекст
Необходимо выбрать, где будет размещен орекстратор -- в отдельном сервисе или часть уже существующего сервиса.

## Рассмотренные варианты

### Вариант (/ Альтернатива) №1 «Отдельный сервис-оркестратор»
 Для орекстрации бизнес процессов (саг) предлагается использовать отдельный сервис.

### Вариант (/ Альтернатива) №2 «Оркестратор -- часть существуещего сервиса»
В рамках этого подхода предполагается использовать уже существующий сервис.



## Сравнение альтернатив
| Вариант решения           | Преимущества                                                 | Недостатки                                                |
|---------------------------|--------------------------------------------------------------|-----------------------------------------------------------|
| Вариант №1 «Отдельный сервис-оркестратор» | Логика управления бизнес-процессом(процессами) сосредоточена в одном месте(сервисе), нет нарушений SRP. Проще разобраться, поддерживать и развивать. Проще подключить(hosted) какой-нибудь bpmn движок.| Накладные расходы на поддержку, деплой, одним словом усложнение для devops.|
| Вариант №2 «Оркестратор -- часть существуещего сервиса» | Часть уже работающего решения, можно быстро добавить необходимый функционал. Нету особых усложнений для devops.| Не подходит в случае сложных саг и бизнесс процессов -- много шагов, длительность операций. Нарушения SRP. Подходит только для очень простых сценариев, несложных компенсаций. |

## Принятое решение
Критерии: сложность сущ. процессов, потенциал для усложнения\развития процессов, возможность использовать сущ. на рынке решения(bpmn), скорость реализации соотв. функцинала.
Практически по всем параметрам -- разве что кроме скорости реализации, которая на данный моммент не критична, т.к. MVP уже в каком-то виде работает -- выбран вариант делать оркестратор **отдельным сервисом**. Существующие бизнес-процессы компании довольно сложны, много шагов, шаги могут быть разной длительности, возможны сложные компенсации и\или ручное вмешательсво. Не будет нарушений SRP для сущ. сервисов компании. Усложнение инф-ры кажется не существенным фактором, тем более ради такого важного функционала.
В общем, при выбранных критериях и условиях, выбор очевиден и он сделан в пользу отдельного сервиса-орекстратора.
